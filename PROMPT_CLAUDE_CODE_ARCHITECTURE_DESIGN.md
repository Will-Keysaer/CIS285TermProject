# Prompt 2 — Claude Code: Independent Architecture and Design Proposal

**How to use:** Run Claude Code from the repository root after the Spec Kit run has completed, but do not give Claude Code the Spec Kit-generated artifacts as input. The prompt deliberately tells Claude Code to create a separate output directory so that it cannot overwrite Spec Kit's work.

```text
Act as a senior software architect preparing an independent architecture and design proposal for the SplitSmart CIS 285 term project.

OBJECTIVE
Independently analyze the customer requirements and clarified specification, then create a complete architecture/design package. This is a parallel proposal that will later be compared with a separate Spec Kit-generated proposal. Do not implement the application.

INDEPENDENCE REQUIREMENT
Do not read, quote, copy, or use any architecture/design artifacts generated by Spec Kit. In particular, do not inspect its `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, or generated diagrams. Work only from the authoritative source documents listed below and the existing project configuration/constitution. If the Spec Kit artifacts are present, leave them untouched and do not use them to influence your decisions.

AUTHORITATIVE INPUTS
Read these files completely:
1. `UserRequirement.md`
2. `specs/001-splitsmart-expense-sharing/spec.md`
3. `.specify/memory/constitution.md`

You may inspect repository configuration and existing source files only to understand what actually exists. Do not assume application code or infrastructure exists unless you find it.

SOURCE PRECEDENCE
- `UserRequirement.md` is the authoritative customer baseline.
- `spec.md` is the clarified feature specification and records acceptance criteria, assumptions, and open questions.
- `constitution.md` supplies engineering constraints and governance.
Do not turn implementation preferences into customer requirements.

CRITICAL PLATFORM CONFLICT
The customer requires a primarily web-based product. The constitution explicitly states that Swing is an implementation decision and that a Swing-only desktop application does not satisfy the web requirement. The specification's Open Question 1 asks whether the customer approves a Swing desktop MVP or requires the MVP itself to be web-based.

You MUST preserve this conflict. Do not decide on the customer's behalf that Swing is acceptable. Your architecture must:
- Identify the platform decision as unresolved and potentially blocking.
- Analyze at least two alternatives:
  A. A primarily web-based architecture that satisfies the stated customer baseline.
  B. A Java Swing desktop MVP only if documented customer approval authorizes that change in delivery platform/scope.
- Compare their requirement coverage, components, deployment, security, user experience, testing, and likely complexity.
- Explain the implications of choosing each alternative.
- Mark the Swing path as conditional on explicit customer approval.
- Do not claim that a Swing-only application satisfies NFR-001.
- Avoid blending the alternatives into an unclear hybrid architecture.

ENGINEERING CONSTRAINTS
- Java 21 and Maven for Java application code.
- JUnit 5 and Maven verification for automated tests.
- Object-oriented separation of presentation, application/business logic, and infrastructure/persistence. Business rules must be testable without launching a GUI.
- `BigDecimal` for all monetary values and calculations; no binary floating-point money.
- Explicit currency precision, rounding, and persistence rules.
- Percentage splits: nonnegative percentages totaling exactly 100%, with fractional cents distributed by largest remainder.
- Equal splits must reconcile exactly to the supported currency precision.
- Pending expenses do not affect balances; approved expenses do; rejected expenses do not.
- Recording a payment immediately changes the corresponding balance, and the record must preserve sender, recipient, amount, date, recorder, and record timestamp.
- A group's payer must be a group member, selected separately from participants, and may not be a participant.
- Respect group creator/manager membership permissions, invitation acceptance, group boundaries, privacy, and authorization.
- PlantUML for maintained diagrams when diagrams are useful.
- AI output must be reviewed by a human before acceptance.

CUSTOMER FUNCTIONAL SCOPE
Retain and account for all of the following:
- User accounts, sign-in, and account recovery.
- Group creation and management, invitations, invite acceptance, and membership roles.
- Expense creation, payer, participants, equal and percentage splits, optional receipt images.
- Group expense notifications.
- Expense review and approval.
- Pairwise balances.
- Payment tracking and immediate balance updates.
- Expense, balance, and payment reports/summaries, including date-range reports.
- Primary web-based delivery.

The specification describes a candidate narrower Swing MVP and deferred features. It is not permission to erase customer scope. Clearly label full product scope, candidate MVP scope, deferred work, and decisions requiring customer approval.

OUTPUT LOCATION
Create your independent proposal under:
`architecture/claude-code/`

Do not put your artifacts in the Spec Kit output directory. Do not overwrite or modify:
- `UserRequirement.md`
- `specs/001-splitsmart-expense-sharing/spec.md`
- `.specify/memory/constitution.md`
- Any Spec Kit-generated output.

DELIVERABLES
Create the following files under `architecture/claude-code/`:

1. `architecture.md`
   - Executive summary and scope.
   - Platform alternatives and decision analysis.
   - Recommended architecture for each viable alternative, clearly distinguishing conditional recommendations.
   - Logical architecture, layers, modules/components, responsibilities, dependencies, and boundaries.
   - Major user workflows and component interactions.
   - Security, privacy, authorization, and data ownership.
   - Persistence, transaction, consistency, and error-handling considerations.
   - Deployment/runtime considerations.
   - Risks, trade-offs, assumptions, and open decisions.
   - Constitution compliance assessment.

2. `research.md`
   - Technical decisions and rationale.
   - Alternatives considered.
   - Evidence/sources for any external research actually performed.
   - Unknowns and decisions requiring customer input.
   - Do not fabricate citations, benchmarks, or research.

3. `data-model.md`
   - Domain entities, attributes, identifiers, relationships, constraints, and lifecycle/state transitions.
   - Include Account, Group, Membership/Invitation, Expense, ExpenseParticipant/Allocation, ReviewDecision, Notification, Balance or balance derivation, Payment, and Report as appropriate.
   - Explain whether balances are derived, materialized, or both and why.
   - State invariants for money, expense approval, payer/participant roles, and payment reconciliation.

4. `contracts/`
   - Define the appropriate interface contracts for the platform alternatives (for example, REST/API contracts for a web architecture and UI/application-service contracts for a Swing alternative).
   - Include request/response or input/output structures, validation, authorization, errors, and relevant state behavior.
   - If a contract is conditional on the platform decision, label it clearly.

5. `quickstart.md`
   - Prerequisites, setup, build/run/test commands, and end-to-end validation scenarios.
   - Do not claim commands have been tested unless you actually run them successfully.
   - If implementation does not yet exist, clearly distinguish proposed commands from verified commands.

6. PlantUML source files under `diagrams/` when useful:
   - System/context or component architecture.
   - Domain/entity relationships.
   - Sequence diagrams for expense submission/approval and payment recording.
   - Keep diagrams consistent with the written artifacts.

7. `traceability.md`
   - Map FR-001–FR-012 and NFR-001–NFR-005 to the architecture components/design decisions and proposed verification.
   - Include AC-001–AC-023 where useful.
   - Explicitly identify any requirement not addressed by the candidate MVP and explain why it remains in the full customer scope.

DESIGN EXPECTATIONS
- Make decisions explicit, not generic.
- Separate facts from recommendations and assumptions.
- Do not invent technology already selected by the customer.
- If recommending a database, framework, authentication mechanism, hosting approach, or notification channel not specified by the requirements, label it as a proposal and explain alternatives.
- Address monetary precision and reconciliation in enough detail to guide implementation.
- Address concurrency and transactional consistency where simultaneous expense approvals or payments could affect balances.
- Address authorization at both user/group boundaries and relevant operations.
- Include testable acceptance/verification scenarios.
- Avoid overengineering and avoid designing features not supported by the requirements.
- Ensure all documents agree with one another.

VALIDATION AND SAFETY
- Review the generated files for internal consistency and requirement coverage.
- Do not modify the source requirements or constitution.
- Do not write application implementation code.
- Do not commit, push, create a pull request, or modify the Spec Kit proposal.
- Report any files created, checks performed, unresolved platform decisions, and assumptions.

FINAL RESPONSE
Summarize the proposed architecture, the platform alternatives, major design decisions, unresolved questions, exact output paths, and validation performed. Explicitly confirm that this is an independent proposal and that no commit was made.
```
