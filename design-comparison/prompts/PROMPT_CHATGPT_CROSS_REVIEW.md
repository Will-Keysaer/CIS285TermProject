# Prompt 3 — ChatGPT: Independent Comparison, Cross-Check, and Findings Report

**How to use:** Run this only after both generators have finished. Keep both output sets in the repository (or provide the complete files to ChatGPT). Ask ChatGPT to inspect the repository's source documents and both proposals. Do not ask it to merge or rewrite the proposals until the comparison report is complete.

```text
Act as an independent senior software architecture reviewer and requirements auditor for the SplitSmart CIS 285 term project.

TASK
Compare the architecture/design output generated by Spec Kit with the independent architecture/design output generated by Claude Code. Perform a rigorous cross-check against the original customer requirements, clarified feature specification, and project constitution. Produce a factual comparison and actionable findings report. Do not assume either AI-generated proposal is correct.

REPOSITORY SOURCE DOCUMENTS
Read these authoritative documents first:
1. `UserRequirement.md`
2. `specs/001-splitsmart-expense-sharing/spec.md`
3. `.specify/memory/constitution.md`

PROPOSAL SETS
Find and inspect the complete Spec Kit output generated by the planning workflow. Expected artifacts include `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, and any generated diagrams. Use the actual paths reported by Spec Kit; do not assume a path if the repository shows otherwise.

Inspect the independent Claude Code output under:
`architecture/claude-code/`
Expected artifacts include `architecture.md`, the required detailed `design.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `traceability.md`, and any diagrams. Review `architecture.md` for high-level architecture and `design.md` for concrete component/class design, interfaces, workflows, financial algorithms, transactions, and error handling. Do not assume Spec Kit must have a `design.md`; assess its detailed design from the artifacts it actually generated.

If an expected file is missing, report it as missing. Do not silently fill gaps or infer that an artifact exists.

SOURCE PRECEDENCE AND REVIEW RULES
- `UserRequirement.md` is the authoritative customer baseline.
- `spec.md` elaborates the requirements and records clarifications, acceptance criteria, assumptions, and open questions.
- `constitution.md` supplies engineering constraints and governance.
- Spec Kit and Claude Code outputs are proposals, not authoritative requirements.
- Do not treat agreement between two AI tools as proof of correctness.
- Do not allow an implementation recommendation to silently change a customer requirement.
- Distinguish confirmed source facts, reasonable design recommendations, assumptions, and unresolved customer decisions.
- Do not modify any source or proposal files during the review. Produce a separate report only.

CRITICAL PLATFORM-COMPLIANCE CHECK
The customer requires a primarily web-based product. The constitution states that Swing is an implementation decision and that a Swing-only desktop application does not satisfy the web requirement. The specification's Open Question 1 asks whether the customer approves a Swing desktop MVP or requires the MVP itself to be web-based.

Check both proposals carefully:
- Does either incorrectly claim that a Swing-only app satisfies the customer requirement?
- Does either assume customer approval that is not documented?
- Does either clearly present a web-based alternative and a conditional Swing alternative?
- Does either mark the platform choice as unresolved and potentially blocking?
- Does either distinguish full customer scope from the candidate MVP and deferred features?
Treat any silent replacement of web delivery with Swing as a critical finding.

REVIEW DIMENSIONS

A. Requirements completeness
- Map every FR-001 through FR-012 to architecture components, data model, contracts, and verification.
- Map NFR-001 through NFR-005.
- Check AC-001 through AC-023 for coverage in proposed workflows and validation.
- Check all original feature areas in `UserRequirement.md`.
- Identify omitted, weakened, contradicted, or incorrectly reinterpreted requirements.
- Check whether optional receipt images, account recovery, notifications, approvals, reports, and date-range filtering are accounted for.

B. Constitution compliance
Verify:
- Java 21 and Maven are respected for Java application code.
- JUnit 5 is the automated test framework.
- Presentation/UI is separated from business logic.
- Business rules are testable independently of the GUI.
- All money uses `BigDecimal`; no `float`/`double` monetary calculations.
- Currency precision and rounding are explicit.
- PlantUML is used for diagrams where useful and maintained consistently.
- AI output is presented as requiring human review.
- Swing is not treated as a customer requirement or as satisfying the web requirement without approval.

C. Domain model and financial correctness
Inspect:
- Account, group, membership/invitation, expense, payer, participants, allocations, review decision, notification, balance, payment, and report modeling.
- Payer is selected separately from participants, must belong to the group, and may be excluded from the allocation.
- Equal split behavior and remainder handling.
- Percentage validation (nonnegative, exactly 100%).
- Largest-remainder cent allocation and deterministic tie-breaking.
- Exact reconciliation of allocation shares to expense total.
- Pending/rejected/approved expense behavior.
- Payment behavior: sender records it, it immediately affects balance, and history records sender, recipient, amount, date, recorder, and record timestamp.
- Whether balances are derived, materialized, or both, and how consistency is maintained.
- Duplicate submissions/payments, overpayments, concurrent operations, and audit/history concerns.

D. Architecture and detailed-design quality
Compare:
- Platform and deployment model.
- Layers, modules, component responsibilities, and dependency direction.
- UI-to-business-logic separation.
- Persistence and transaction boundaries.
- Authentication, authorization, privacy, and group-level access controls.
- Notification approach.
- Receipt image handling.
- Reporting approach.
- Error handling and validation.
- Performance assumptions and NFR-004 feasibility.
- Maintainability, testability, complexity, and scope control.
- Claude Code's `design.md` for sufficient implementation detail, including component/class responsibilities, interfaces, workflows, state transitions, monetary allocation, transaction handling, and verification scenarios. Compare this detail against the corresponding Spec Kit artifacts even if Spec Kit has no standalone `design.md`.

E. Contracts and diagrams
- Check contracts against the data model and workflows.
- Check naming, types, validation rules, errors, and authorization.
- Check that diagrams match the written architecture and each other.
- Identify missing contracts or diagrams that are necessary to communicate important design decisions.
- Do not require diagrams merely for decoration.

F. Research quality
- Check whether cited sources exist and actually support the stated decisions, to the extent verifiable.
- Flag unsupported claims, invented benchmarks, vague “industry standard” assertions, and unexplained technology choices.
- Identify where more research or customer input is required.

G. Internal consistency and implementation readiness
- Check that plan/architecture, Claude Code's `design.md`, data model, contracts, quickstart, and traceability agree.
- Identify ambiguous decisions that would cause developers to implement incompatible behavior.
- Identify missing details that should be resolved before implementation.
- Check that proposed quickstart commands are accurate and distinguish tested commands from suggestions.

COMPARISON METHOD
1. Build a requirement-by-requirement coverage matrix.
2. Build a side-by-side comparison of major architecture and design decisions.
3. Identify areas where both proposals agree, where they differ, and where both may be wrong.
4. Independently judge each design against the source documents; do not award correctness based on majority agreement.
5. Prioritize findings by severity:
   - CRITICAL: violates or silently changes a customer requirement, constitutional principle, or core financial invariant.
   - HIGH: major missing behavior, security flaw, data inconsistency, or design gap likely to block implementation.
   - MEDIUM: meaningful ambiguity, maintainability/testability concern, or incomplete contract.
   - LOW: documentation clarity, minor consistency, or polish issue.
6. For every finding, cite the exact source file and section/requirement ID, identify which proposal(s) are affected, explain the consequence, and recommend a concrete correction.
7. If the available evidence does not support a conclusion, state what is unknown rather than guessing.

REPORT OUTPUT
Create a new file:
`architecture/CROSS_REVIEW_REPORT.md`

The report must include:

1. Executive summary
   - Overall assessment of each proposal.
   - Whether either proposal is ready to guide implementation.
   - The most important blockers.

2. Source baseline
   - List the source documents and proposal artifacts reviewed.
   - Note any missing or unavailable artifacts.

3. Requirement coverage matrix
   - Rows for FR-001–FR-012 and NFR-001–NFR-005.
   - Columns for customer meaning, Spec Kit coverage, Claude Code coverage, gaps/conflicts, and verdict.
   - Include AC references where helpful.

4. Architecture and detailed-design comparison
   - Side-by-side comparison of platform, components/layers, data/persistence, security, notifications, reports, deployment, testing, and major trade-offs.
   - Explicitly compare Claude Code's `design.md` with the equivalent detailed design across Spec Kit's actual artifacts; do not penalize Spec Kit solely for lacking a file named `design.md`.

5. Critical and high-priority findings
   - Finding ID, severity, affected proposal(s), source evidence, explanation, impact, and recommended action.

6. Medium/low findings
   - Same structure, concise where appropriate.

7. Domain and financial-integrity audit
   - Explicitly assess allocation, rounding, approvals, balances, payments, and concurrency.

8. Constitution compliance table
   - Each principle/constraint, Spec Kit result, Claude Code result, evidence, and verdict.

9. Agreement and disagreement analysis
   - Sound agreements.
   - Meaningful differences.
   - Cases where both proposals share the same incorrect assumption.

10. Recommended direction
   - Recommend which design elements to retain, reject, or revise.
   - Do not choose the unresolved product platform on the customer's behalf.
   - State the exact customer decision needed to resolve the web-versus-Swing issue.
   - Identify any design decisions that can proceed independently of that decision.

11. Readiness checklist
   - What must be corrected or clarified before implementation.
   - What can safely proceed.
   - What needs customer approval.
   - What needs human review.

12. Final verdict
   - `READY`, `READY WITH CONDITIONS`, or `NOT READY` for implementation planning.
   - Explain the verdict and list blocking conditions.

IMPORTANT
- Be critical but fair. The goal is not to make the two proposals agree; it is to identify the most correct, complete, and implementable design.
- Do not modify the source requirements, constitution, Spec Kit output, or Claude Code output.
- Do not write application code or commit anything.
- Do not claim to have executed tests/builds unless you actually did so.
- Keep the report actionable, traceable, and specific to this repository.
- At the end, list exactly which files were reviewed and the report path.
```
